# 架构

## 三条设计原则

这三条决定了所有的技术选择。有冲突时按这个顺序让步。

### 1. 规则层先算，模型后说

**所有数值结论都由确定性代码得出。语言模型只负责解释，不允许它算数。**

这不是为了省 token，是因为语言模型在健康数字上会犯错，而且犯得很像对的：
把 71.2 和 74.0 的差写成 2.0 kg，把「体脂率下降 5.4 个百分点」说成「下降 54%」，
或者给你一个报告里根本没出现过的数字。这类错误的后果是用户据此改变训练和饮食。

所以流水线是：

```
原始数据 → 解析 → 归一 → 聚合/趋势（analysis）→ 规则判定（pitfalls）
                                                      ↓
                                            build_facts()  ← 结构化摘要，只含算好的数
                                                      ↓
                                              LLM 只读这份摘要写文字
                                                      ↓
                                build_report() 把确定性结论 + AI 文字拼成报告
```

关键约束：`narrate()` 拿到的是 `build_facts()` 的输出，**里面没有任何原始观测**。
模型看得见的数字，和你自己 `--json` 导出后能看见的**完全一样**。这是可审计的。

而且 **AI 那一节是可选的**：没有 key、网络不通、模型返回垃圾，
报告依然完整——因为它所有的结论在第五节「规则层结论」里已经由代码写好了。
AI 顶多是在旁边多写一段白话。

### 2. 不知道就说不知道

没有参考区间 → 判定列写「只做趋势」，报告里专门开一节列出来。
数据点不够 → 列进「不足以判断的部分」。
变化量小于噪声 → 明写「视为基本未变」。
设备的百分比基准可能变了，但**没有量化证据** → 只给 info 级口径提醒，
不升级成 warn（详见 [PITFALLS.md](PITFALLS.md) 第 5 条）。

硬编一个"正常"出来，比留白伤害大得多。

### 3. 本地优先

默认完全离线。联网只发生在用户显式开启 AI 解读时，且只发结构化摘要。
见 [PRIVACY.md](PRIVACY.md)。

## 模块地图

```
src/health_report/
├── model.py        统一数据模型：Observation / Workout / Dataset / RefRange
├── catalog.py      ★ 指标目录：别名解析、单位、聚合方式、参考区间（含出处）、哪一侧值得留意
├── units.py        单位换算（查不到返回 None，不猜）
├── parsers/
│   ├── __init__.py 类型探测与分发
│   ├── apple.py    Apple 健康导出（流式，可吃几 GB；含睡眠分期与睡眠时刻指标）
│   ├── inbody.py   InBody 长格式报告（含设备自带参考区间）
│   └── generic.py  通用长格式 CSV（任何设备的万能入口）
├── analysis.py     ★ 趋势计算 + 睡眠规律性 + 指标关联 + 设备接替探测
├── pitfalls.py     ★ 数据陷阱规则层（13 条规则，带稳定机器码）
├── report.py       Markdown 报告 + build_facts（发给模型的摘要）
├── llm.py          ★ AI 解读层：四种后端自动探测 + 数字溯源硬校验
├── privacy.py      设备名脱敏（人名识别与替换）
├── samples.py      合成数据生成（demo 的输入 / 测试夹具 / examples 的来源）
└── cli.py          命令行入口
```

`★` 标记的四个文件是这个项目真正的资产。`parsers/` 是苦活，`report.py` 是排版。
**价值集中在"指标怎么归一""哪些数字不能比""模型说了算不算"这三件事上。**

> `llm.py` 曾经真的只是"三十行胶水"（一个 OpenAI 兼容客户端）。现在它是一个完整的
> 子系统，因为接任何模型都绕不开两个问题：**后端怎么选**（客户不该为了用这个工具去申请
> API key），以及**它编数字怎么办**（见下方「数字溯源」）。它现在是这个仓库里最长的文件。

## 数据流

```
export.zip ──┐
inbody.csv ──┼→ parsers ──→ Dataset（统一单位、统一指标 ID、参考区间跟着观测值走）
generic.csv ─┘                    │
                                  ├─→ analysis.analyze()  ─→ Analysis（数字 + 判定枚举）
                                  │                              │
                                  └─→ pitfalls.check()  ─────────┤
                                                                 ↓
                                              report.build_facts()  → dict（JSON 可序列化）
                                                                 ↓
                                                        llm.narrate()（可选）
                                                                 ↓
                                              report.build_report() → Markdown
```

### 为什么参考区间挂在 Observation 上，而且必须同源

`Observation.ref` 保存**输入自带的**区间（InBody 报告印的"报告参考范围"）。
`analysis` 的选择顺序是：

```
被判定的那条观测自带  >  同一 source 最近一条自带  >  内置人群表  >  无
```

（实现在 `analysis.ref_for_observation()`，它是唯一决定"用哪个区间"的地方。）

医生看的化验单上每个项目都有自己的参考范围。体成分设备同理——它用的是自己的模型和
自己的人群。而且用户手上的纸质报告印着的就是那个区间，报告里用别的区间会让人对不上。

**但"设备自带优先"有一个前提：区间只能用于它自己那台设备的读数。** 家用秤报 21.2%
体脂，InBody 的区间是 10~20%——两者都不是为对方标定的。把它们配在一起会得出一个
看起来专业、实际无意义的"高于参考上限"。所以区间必须与读数同源，跨设备就退回内置人群表。

**那么什么时候才该放弃判定？** 这里有一个**改对过的判断**，值得记下来：

早期版本写的是"同一指标出现 >1 个 source 时，直接不做判定"。它在 Apple 数据上
**触发过宽**——实测一份真实导出里 17 条提示有 15 条是「来源不一致，不做判定」，
几乎所有可判定指标都被压掉，报告等于没有内容可交付。

错在哪里：**判定算的是「最新值 vs 与它同源的区间」，这件事多来源并不妨碍**
（同源约束已经由 `ref_for_observation` 保证了）。多来源真正影响的是**跨时间的可比性**，
那属于趋势，不属于判定——那件事由 `DEVICE_HANDOVER` 规则单独讲。

所以现在的判据只在**一种**情形下放弃判定：**这个指标确实存在可用区间，但被判定的那条
观测的来源提供不了它**——也就是"有尺子，却不能拿来量这个读数"。判据落在
`MetricTrend.range_available` 上（注意它和"本次判定用的 ref"是**两个不同的东西**：
体重可能设备给过区间、但最新读数来自另一台没给区间的设备，于是
`ref is None` 而 `range_available is True`）。

`verdict == "na"` 有三种原因，报告层的措辞必须区分——不能一律写成"只做趋势"：

| `verdict_note` | 含义 | 报告措辞 |
|---|---|---|
| `无可用参考区间` | 口径问题，这台设备就是没有公认区间 | 只做趋势 |
| `来源不一致，不做判定` | **有区间但同源拿不到**，是数据问题，更要紧、更该显眼 | 来源不一致，不做判定 |
| `该指标不参与判定` | 生物电阻抗、设备建议等原始读数 | 不参与判定 |

### 并发与接替是两件事

同一指标的多来源有两种完全不同的形态，混为一谈会同时犯两种错：

| 形态 | 含义 | 影响 | 谁负责 |
|---|---|---|---|
| **并发** | 同一段时间被两台设备各记了一遍 | **数值口径**（累计类会被双计） | 解析器的 `--source-policy` |
| **接替** | 不同时期用不同设备 | **跨时间可比性**（台阶不是身体变化） | `DEVICE_HANDOVER` 规则 |

`analysis.source_structure()` 用启发式区分它们（同日多来源天数 ≥ 7 → 并发），
并找出接替点。**这是启发式，代码注释里写明了它的用途是"提示"而不是"断言"**——
宁可多提示一条（代价是一条 info），也不要漏掉，因为漏掉会让"换设备造成的台阶"
被读成生理变化。它踩过一个坑：合并短碎片之后前后两段可能变成同一来源，
若不再次合并会造出「A 接替 A」这种假接替点。

### 为什么聚合在解析阶段做，趋势在分析阶段做

Apple 的原始数据里，心率一天有几千条。如果把它们都塞进 `Dataset`，
一份几年的导出会吃掉几 GB 内存。所以解析器按 `(metric, date)` 聚合，
聚合方式由 `catalog` 里的 `agg` 决定：

| `agg` | 含义 | 例子 |
|---|---|---|
| `sum` | 当日累加 | 步数、活动能量、步行距离（一天几十条分段记录，**必须**累加） |
| `mean` | 当日平均 | 心率 |
| `snapshot` | 当日取时间戳最晚的一条 | 体重、静息心率、体脂率 |

**这个区分是有代价的教训**：把"步行距离"当快照处理会只剩最后几米的记录，
把全天距离算成 0.02 km。

然后 `analysis` 再处理跨日的趋势。两级分工明确：解析器只管"这一天这个指标是多少"，
分析层只管"这段时间它怎么变"。

### 为什么 `sum` / `mean` 类指标不算首末差值

把两天的步数相减没有意义。所以这类指标的 `delta` / `pct` / `per_30d` 一律为 `None`，
改为给 `mean`（有数据日的平均）、`daily_mean`（总和 ÷ 全部跨度天数）、
`coverage`（覆盖率）。报告里显示"日均 X"，而不是"从 A 到 B"。

## 扩展点

### 加一个指标

在 `catalog.py` 的 `_SPECS` 里加一条 `MetricSpec`。需要给的：

```python
MetricSpec(
    "body_mass", "体重", "kg", "体成分",
    precision=1,             # 报告里显示几位小数
    noise=0.3,               # 小于这个变化量视为测量噪声
    aliases=("体重", "weight", "body mass"),   # 别名匹配用（长别名优先）
    apple_types=("BodyMass",),                 # Apple 的类型名，省掉公共前缀
    ref_low=..., ref_high=..., ref_source="...", ref_kind="range",
    ref_fn="body_fat",       # 需要年龄/性别时用函数
    hint="...",              # 报告里显示的一行解释
)
```

**别名匹配是长别名优先的**，所以 `目标体重` 不会被 `体重` 吃掉、
`骨骼肌指数SMI` 不会被 `骨骼肌` 吃掉。加别名时注意这一点。

### 加一个数据来源

见 [DATA_FORMATS.md](DATA_FORMATS.md) 结尾。写一个返回 `Dataset` 的函数，
在 `detect_kind()` 里加一条规则。**分析层和报告层一行都不用改**——它们只认 `Dataset`。

### 加一条数据陷阱规则

在 `pitfalls.py` 里写一个函数，返回 `Finding` 列表，注册进 `check()`。要求：

- `code` 是稳定的机器码（用户会按它过滤，改了就是破坏性变更）
- `severity` 只用 `info` / `warn` / `alert`，且 alert 要极度克制
- `title` 必须带具体数字，`detail` 必须说清"为什么"和"该怎么读"
- **不许出现诊断性措辞**（"你患有"、"建议服用"）
- 也要能优雅处理数据几乎为空的情况

新规则请顺手在 `docs/PITFALLS.md` 里补一节，并在 `tests/` 里加一个能触发它的用例。

## AI 解读层：两个绕不开的问题

`llm.py` 存在的意义不是"加个 AI"，而是解决两个具体的落地障碍。

### 一、客户不该为了用这个工具去申请 API key

所以后端是**自动探测**的，但**自动探测有一条隐私红线**：`auto` 只会采用
**不出本机**或**用户已显式配置**的后端。

| 顺序 | 后端 | 数据去哪 | `auto` 会采用？ |
|---|---|---|---|
| 1 | 环境变量配置的云端端点（任何 OpenAI 兼容服务） | 你配的地址 | ✅（配了 = 知情） |
| 2 | 本机模型（Ollama / LM Studio / llama.cpp，只连回环） | **不出本机** | ✅ |
| 3 | 本机已装的 AI 工具（DSH / Claude Code / Codex） | 对应厂商 | ❌ 需 `--llm` 或 `--ai-backend` |
| 4 | 都没有 | 纯规则报告 | —— |

**CLI 后端一律 `is_local=False`、`sends_to` 写厂商名。** 这条不能含糊：那些工具是
**本地客户端、模型在云端**，用它们等于把算好的摘要发给对应厂商。

> **为什么第 3 类不能自动采用**（实测踩到）：早期版本让 auto 一路探测到底，于是在装了
> DSH 的机器上，`health-report report 导出.xml`（**既没配 key、也没加 `--llm`**）
> 会**静默把健康摘要发给 DeepSeek**。而 `docs/PRIVACY.md` 那张「什么时候会联网」的表里，
> `report 文件` 写的是"不"。对一个自称隐私优先的工具来说，**默认静默外发是不能接受的**。
> 现在必须显式开口（`--llm` / `--ai-backend dsh`），本机模型则不需要——因为它不出机器。
> 回归测试：`tests/test_llm_backends.py::TestAutoNeverLeaksData`（用 red-green 验过：
> 把限制去掉，`test_auto_refuses_a_cloud_cli_agent` 立刻失败）。

CLI 后端的调用有几条是实测踩出来的，都写在代码注释里：

- **必须在系统临时目录里跑**（只放一份 `facts.json`）。它们本质是**编码 agent**，
  会读写文件、执行命令，绝不能在用户的原始数据目录里跑。
  *（曾经反过来对 DSH 优先用它自己的配置目录，结果一旦那个目录异常，
  沙箱会让 `mkdir` **挂住而不是报错**，整个测试套件从 1.5 秒变成永不结束。
  可能永久挂死的测试套件比"AI 偶尔读不到数据"严重得多，所以顺序调了回来。）*
- **stdout/stderr 用文件重定向，不用管道**：受限沙箱下命名管道可能被拒绝。
- **facts 走文件，不走命令行**：真实摘要 32–39 KB，**超过 Windows 的 32767 字符上限**，
  塞进 argv 必然失败。另有 `_CLI_ARGV_LIMIT` 护栏提前挡住。
- **不重试**：CLI agent 冷启动就要十几秒，重试会让用户以为卡死。
- **agent 可能把正文写成文件**（实测 DSH 会把说明写成 `健康数据说明.md`，stdout 只剩
  一句过程叙述），所以要收集它自己写的文本文件并按"能溯源多少数字"打分挑选。
- **agent 可能反过来索要数据**（"请把 facts 贴给我"）。这类文字**绝不能**进报告——
  用户会以为那就是解读。判据是"命中索要措辞"且"没有一个数字能在摘要里溯源"。

### 二、模型编数字怎么办

**这是硬约束**：AI 写的每个数字都要能在 `facts` 里找到出处，否则不许进报告。

- 找不到来源 → **含那个数字的整句被删掉**，其余保留，报告里注明删了几处。
- 删完剩下的不足 120 字符 → 整段丢弃，改用规则层原文。
- **宁可报告里没有 AI 那一段，也不能出现一个编造的数值。**

但**误杀比漏抓更糟**（把一整段正确的解读丢掉）。真机实测一次输出被删了 13 处句子，
逐条看下来大量是合法写法。所以这些被判为可溯源：

| 合法写法 | 例子 |
|---|---|
| 千分位（逗号或**空格**） | `1,910` / `11 534` |
| 量级后缀 + 保留 k 位有效数字 | `1086 万` ← `10862753` |
| 按位舍入 | 真值 `6.28937…` 写成 `6.29` |
| Markdown 小节号 | `### 2.2` |
| 容器长度 | 「共 29 个指标」← `len(metrics)` |

而**编造的测量值照样被抓住**：摘要里是 `61.0`，写 `58.2` → 删。

> **这一层最重要的教训**：真机上那 13 处里，`704 小时`、`20.2 万 kcal`、
> `280 万条原始记录` 全是**模型算对了、而我们没给它**的数字。
> 摘要只给了各训练类型的明细，总量得模型自己加；记录条数解析器数了却没传到报告层。
> 这违背了本项目最基本的分工——**规则层算，模型只叙述**。
> 少给一个总量，就是逼模型自己算，然后又不认它算的结果。
> 修法是**把该给的汇总补进摘要**（`workouts.total_hours` / `data.record_count` /
> `metrics[].coverage`），并在提示词里明确禁止模型自己做加法与百分比换算。

## 测试策略

- **零依赖**：用标准库 `unittest`，不引入 pytest。零依赖是这个项目的卖点之一，
  测试框架也不该破坏它。`python -m unittest discover -s tests`
- **合成夹具**：`samples.py` 里的合成数据**故意埋了陷阱**，
  每一处都对应一条规则（对照表在 `samples.py` 的模块 docstring 里）。
  规则层测试直接断言这些陷阱能被抓到。
- **自检脚本**：`tools/_check_*.py` 是端到端的独立自检（解析、分析、报告、多来源口径、
  睡眠时刻指标、AI 层）。**单测里不许有真实网络或真实子进程调用**，
  真实探测只发生在自检脚本里。
- **CI 端到端**：每次 push 都跑 `health-report demo`，并断言报告里
  确实有免责声明和规则层结论；`examples/` 必须与生成器逐字节一致
  （报告那一条比对时会剔掉"生成时间"行）。
- **隐私守卫**：CI 检查 `git ls-files` 里没有匹配真实数据模式的文件。

## 已知的架构债（v0.1 的范围）

诚实列出来，免得以为是bug：

| 项 | 说明 |
|---|---|
| 报告只有 Markdown | HTML + 内联 SVG 的打印版在路线图上（那才是给客户的交付形态）。纯 Markdown 放不下图 |
| 英文报告未实现 | `build_report` 有 `lang` 参数但只实现了 `zh`。英文版在路线图上 |
| 不支持图片输入 | 体测报告照片需要 OCR/视觉模型。这是最自然的入口（数据本来就在纸上），但要额外成本 |
| `Correlation` 元素不解析 | Apple 导出里的 `<Correlation>` 可能含额外指标（`<ActivitySummary>` 已解析） |
