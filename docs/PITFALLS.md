# 数据陷阱

这个文件比代码更重要。

接一个模型、画几张趋势图，谁都能做。难的是知道**哪些数字不能横着比**。健康数据里
最容易出错的不是"算错了"，而是"算对了但读错了"——两个数字都在，相减也正确，
结论却是错的。

下面每一条都对应代码里一个可执行的检查（`src/health_report/pitfalls.py`），
每条都编了稳定的机器码，方便你在自己的脚本里按 code 过滤。

> **本文举例用的所有数值都是合成的**，只保留陷阱的**结构和量级**。
> 真实体测数据不会进这个仓库。

---

## 总表

| 机器码 | 严重度 | 检测什么 |
|---|---|---|
| `SRC_MIXED` | warn | 同一指标来自多套测量系统，跨来源的差值不是"变化" |
| `SAME_DAY_CONFLICT` | warn | 同一天两台设备测同一指标，差值超过噪声阈值 |
| `HYDRATION_AMPLIFIES` | warn | 体水分超出参考上限，体重/去脂体重的变化被放大 |
| `IMPEDANCE_SHIFT` | warn | 分节段阻抗大幅漂移，该节段的体成分读数可比性下降 |
| `PCT_BASELINE_SHIFT` | warn | 节段百分比的隐含标准值漂移 >5%，百分比跨时间不可比 |
| `PCT_BASELINE_CAVEAT` | info | 出现了节段百分比，提示只比 kg |
| `MASS_BALANCE` | warn | 体成分四项加总 ≠ 体重，该次测量自身不闭合 |
| `DEVICE_HANDOVER` | info | 时间线里有设备接替，跨切换点的变化不可比（合并一条） |
| `RANGE_OUT` | warn / info | 值落在参考区间外（按区间性质区分措辞） |
| `LABEL_CONFLICT` | warn | 设备的文字判定与数值判定不一致 |
| `MISSING_DAYS` | warn | 数据覆盖率 <70%，日均值被系统性低估 |
| `DELTA_BELOW_NOISE` | info | 变化量小于测量噪声，应视为未变 |
| `TREND_TOO_SHORT` | info | 数据点或时间跨度不足以谈趋势 |

严重度的含义是固定的，报告层按它排序：

- **warn** —— 读的时候要注意，可能会误读。（`RANGE_OUT` 在 `range` 性质下也是 warn）
- **info** —— 中性提示。**不是**"你有问题"，而是"这个结论的口径要注意"。
- **alert** —— 这份数据的某个结论不可信，或某项超出筛查阈值需要专业评估。

> **诚实说明**：v0.1 里**没有任何规则产出 `alert`**。把"单次超出筛查阈值"直接提级为
> alert 会夸大事态——单次测量不足以判断。所以相关情形一律留在 `warn`。
> `alert` 这一档保留给将来有明确判据的规则（例如"BMI、腰围、体脂率同时越界"这种
> 多指标一致的证据）。**宁可档位空着，也不制造没必要的焦虑。**

## 1. `SRC_MIXED` —— 多套测量系统混在一起

**现象**：体重同时来自家用体脂秤和 InBody。两条曲线画在一张图上是连续的一条线，
看起来像"体重在稳步下降"。

**为什么是陷阱**：家用秤和 InBody 的绝对值和系统偏差都不一样（生物电阻抗设备之间
差几个百分点很正常）。你看到的那一段"跳变"，可能只是换了台设备，不是身体变了。

**判据**：同一指标出现 ≥2 个 `source`。

**怎么读**：选一台作为**主设备**，长期只用它比较趋势。其它设备的数值只当独立参考点，
不要接在同一条时间线上。

**这个项目的做法**：一旦检测到同一指标有多个来源，就**直接不对它做判定**——
报告里写「来源不一致，不做判定」，并附上这条说明。原因很简单：一个混了两种尺子的
序列上，"正常/异常"这四个字没有意义。宁可留白。

> **例外：按日累加型指标不这么处理。** 见下一节——它们的多来源是**口径**问题，
> 不是分歧，可以确定性地解决。

## 1.5 按日累加型指标会被**双计**（步数最典型）

这一条和上一条的根因不同，后果也更隐蔽。

**现象**：iPhone 和 Apple Watch 会**各自**记录步数，而且时间区间高度重叠——
你身上同时带着两台设备。Apple 健康 App 显示的是去重后的值，但**导出文件里两套记录都在**。
如果解析时按天无条件累加，全天步数就被算高了。

**实测（一份真实导出，1910 天）**：

| | 步数 |
|---|---|
| 有多来源记录的天数 | **1096 天（57.4%）** |
| 无条件累加总计 | 15,634,979 |
| 按主设备取值总计 | **10,862,753** |
| 放大倍数 | **1.44 倍** |
| 最高一天 2025-12-20 | 累加 **90,545** = 45,644 + 44,901 |

两台设备各记了约 4.5 万步——真实值就是 ~4.5 万，而旧口径报了 9 万。

**为什么不能"算对"**：HealthKit 对重叠时间区间的去重算法**没有公开规范**
（按来源优先级取、还是并集，官方文档没有可复现的定义）。所以本项目**不去猜**，
而是把口径变成显式选择，并把差异摆出来：

| `--source-policy` | 含义 |
|---|---|
| `primary`（默认） | 按「主设备优先」取；主设备当天没数据就回退到别的设备 |
| `per-day-max` | 每天取各来源里的最大值 |
| `sum` | 无条件累加（**会算高**，仅用于对照） |

`--prefer-source "Apple Watch"` 可指定主设备。报告里会为每个受影响的指标写一条说明，
给出各口径下的总量和倍数——例如「本次 10,862,753 步，若无条件累加会是 15,634,979
（1.44 倍）」。

**这个错误最坏的地方不是放大倍数，而是它不是均匀偏差**：只有单来源的天数是对的，
多来源的天数被算高。于是"那天戴了哪台设备"污染了逐日对比——包括"步数与睡眠的
相关性"这种分析。

**注意这条与第 1 条的区别**：

| | 快照类（体重、体脂率） | 累加类（步数、距离、能量） |
|---|---|---|
| 多来源意味着 | 两台设备对同一个东西**给了不同的数** → 分歧 | 两台设备把同一段时间**各记了一遍** → 口径 |
| 能不能解决 | 不能（谁对谁错无法判断） | 能，用显式口径 |
| 本项目的做法 | **不做判定**（写「来源不一致」） | 按 `--source-policy` 取值 + 说明差异 |

## 2. `SAME_DAY_CONFLICT` —— 同一天两台设备对不上

**现象**：同一天早上，智能秤读 73.6 kg，InBody 读 71.2 kg，差 2.4 kg。

**为什么是陷阱**：如果不知道这件事，你可能会把"InBody 比秤低 2.4 kg"当成某次
真实变化，或者反过来怀疑其中一台坏了。更麻烦的是：你可能在不知不觉中
**在两个来源之间挑对自己有利的那个**。

**判据**：同一天、同一指标、不同 source，差值超过该指标的噪声阈值。

**怎么读**：这是系统偏差的证据，不是谁错了。记下来，然后固定用一台。

## 3. `HYDRATION_AMPLIFIES` —— 水合状态会改写减重故事

这是**最值得单独讲一条**的陷阱，因为它能让结论方向反转。

**现象**：某次体测的身体总水分超出报告自己印的参考上限。

**为什么是陷阱**：生物电阻抗设备是**通过导电性推算**身体成分的。水分是导电的，
所以水分偏高时：

- 体重会被抬高（真实，但也是暂时的）；
- 去脂体重会被高估（肌肉被"注水"了）；
- 于是同期算出来的"体重下降"被放大，甚至可能出现"体重降了但脂肪没降多少"的假象。

**判据**：`total_body_water` 的最新值超出它自己的参考上限（设备给的或内置的）。

**实测案例（数值已改写）**：某次复核中，两次体测的身体总水分 42.5 L / 44.0 L，
而报告自印上限是 43.4 L——第二次超标 0.6 L。把报告的四个非水分成分相加：

```
水分 + 蛋白质 + 无机盐 + 体脂肪 = 体重   ← 设备自己的恒等式
```

两次都精确闭合。既然骨骼肌在涨、无机盐在涨、蛋白质没变，那"体重下降"里
记在非水分成分上的那部分**只能来自脂肪**。所以：

> **脂肪确实掉了；但"体重掉了多少"这个数字里混着水分波动，不能当真。**

**怎么读**：下次测量统一条件——**清晨、空腹、排空、未运动、未大量饮水、同一时段**。
这一条比换设备重要得多。

## 4. `IMPEDANCE_SHIFT` —— 阻抗漂移是"这次测量条件变了"的告示

**现象**：分节段阻抗在两次测量之间大幅升高（实测案例里下肢 +30% 以上）。

**为什么是陷阱**：阻抗受水合状态、皮肤温度、电极接触、体位影响很大。阻抗漂移
意味着**测量条件变了**，于是该节段的肌肉量/脂肪量读数可比性下降。
换句话说，这一段的"腿掉了 0.7 kg"里，有多少是真实的肌肉流失、
有多少是测量条件差异，**从这两个数字里分不出来**。

**判据**：分节段阻抗指标在最近两次测量间变化超过 **15%** 或 **15 Ω**。

**怎么读**：把这条当作"该节段结论要打折"的标记，而不是"腿掉肌肉"的证据。
需要下一次测量来确认。

## 5. `PCT_BASELINE_CAVEAT` / `PCT_BASELINE_SHIFT` —— 节段百分比跨时间不可比

**这一条我们分了两级，而且刻意让它在真实数据上只报 info。理由值得看完。**

**现象**：设备同时给"左腿脂肪 1.8 kg / 115.1%"和"左腿脂肪 1.5 kg / 94.3%"。
天真的读法是"脂肪降到了正常值的 94.3%"，很有成就感。但 1.5 / 1.8 = 83%，
对应的百分比本该是 115.1 × 0.83 = 95.5%，而报告写 94.3%——**对不上**。

**为什么是陷阱**：那个百分比是「相对该节段标准值」的比值，而**标准值属于设备内部的
参考模型**。厂商可以在固件或算法更新时改动它。用户无法审计这个模型，所以同一个
百分比数字在不同次测量之间**不是同一把尺子**。

**可量化的证据**是"隐含标准值"：

```
baseline = kg 值 ÷ (百分比 / 100)
```

对上面这组：`1.8 / 1.151 = 1.564`，`1.5 / 0.943 = 1.591`，漂移 **+1.7%**。

**判据分两级**：

| 规则 | 条件 | 严重度 |
|---|---|---|
| `PCT_BASELINE_CAVEAT` | 节段同时存在 kg 与百分比两种形式 | **info**（永远报） |
| `PCT_BASELINE_SHIFT` | 隐含 `baseline` 漂移 **> 5%** | **warn** |

**刻意设计的一部分，不是漏检**：在作者复核过的那份真实体测报告上，左右腿肌肉量与
节段脂肪的隐含基准漂移都只有 **0.9% 左右**——**没有量化证据说明模型变过**。
所以 `PCT_BASELINE_SHIFT` 在那份数据上**正确地保持沉默**，只由
`PCT_BASELINE_CAVEAT` 给出 info 级提醒。

为什么这样分？因为原报告作者当时的结论是"设备的参考模型在两次之间被调整过，
腿部肌肉参考值被下调了约 6%"。而按隐含基准反推，这个 6% 是**推不出来**的。
"百分比不可比"这个**结论是对的**，"基准被下调了 6%"这个**量化断言没有数据支持**。

一个健康工具最该克制的地方就在这里：**能证明的说清楚，不能证明的只说口径**。
把统计上不成立的断言写成 warn，会让用户去改变训练计划——那比不报更糟。

**怎么读**：跨时间只比 kg。百分比只在**同一次报告内部**横向比较（比如左腿 vs 右腿、
你的躯干 vs 你的手臂）才有意义。

## 6. `MASS_BALANCE` —— 报告自身是否闭合

**现象**：体成分仪的报告有一个恒等式：

```
身体总水分 + 蛋白质 + 无机盐 + 体脂肪 = 体重
```

**为什么是陷阱**：这条恒等式是设备的自检。**吻合**说明设备没算错；
**不吻合**说明这一次测量本身出了问题（或数据录入有误），那么这一次的
**其它数值也要打折看待**。

**判据**：同一天四项都有值时，`|四项之和 − 体重| > 0.6 kg`。

**怎么读**：不闭合的那一天，不要拿它的任何单项出去和别人比。
先核对原始报告是不是抄错了。

## 7. `RANGE_OUT` —— 超出参考区间，但"超哪个区间"决定了怎么说

**三种区间性质，措辞不能混**：

| 性质 | 含义 | 超出时该怎么说 |
|---|---|---|
| `range` | 正常参考区间 | `高于参考上限` / `低于参考下限` |
| `screen` | 筛查阈值 | `超出筛查参考范围`（并说明这不等于诊断） |
| `goal` | 活动量目标 | **`未达目标`** |

**为什么分开**：这是这类工具最常见的错误。`goal` 和 `range` 混在一起，就会出现
"你今天步数 6500，指标异常"——6500 步不是异常，只是没到常见的建议量。
把公共卫生建议渲染成医学判定，会让用户产生没必要的焦虑。

**真实数据里有个好例子**：一位长期训练的受测者静息心率 54 次/分，低于内置区间的
下限 60。这**不代表异常**——训练者的静息心率本来就常低于 60。所以这条指标的
`ref_note` 会原样出现在报告里，把"低于下限"这个机械判定配上正确语境。

**没有参考区间就只做趋势**：`hrv_sdnn`（心率变异性）、`sleep_deep`（深睡时长）
等指标**没有公认的通用正常范围**——个体差异太大，跨人比较没有意义。
这些指标的报告判定列会写「只做趋势」，报告里还有专门一节列出它们。
**"不知道"是一个合法输出。**

### 还有一层：不是所有"越界"都值得报警

上面讲的是"超哪个区间"，还有一层更隐蔽：**同一个区间，两侧的意义不一样**。

有些指标只有**一侧**是真正需要留意的信号，落在另一侧是常见、甚至好事：

| 指标 | 值得留意的一侧 | 另一侧是什么 |
|---|---|---|
| 静息心率 | 偏高 | 偏低——长期耐力训练者的常态 |
| 去脂体重 / 骨骼肌量 / 蛋白质 | 偏低 | 偏高——肌肉量充足 |
| SMI / VO₂max / 血氧 | 偏低 | 偏高——能力/供氧好 |
| 腰围 / 腰臀比 / 内脏脂肪 / 体脂率 / 体重水分 | 偏高 | 偏低——不构成风险提示 |
| BMI | **两侧都留意** | 偏低是偏瘦，也要看 |

把不需要留意的那一侧也报成"异常"，代价不只是多一条无用提示——**它会把真正该看的
那条淹没**。实测依据：一份 1336 天的真实 Apple 导出里，静息心率中位 56、
**78.7% 的天数低于 60**。旧口径会把几乎每一天都报成「超出筛查参考」。

所以这类越界会被**降调为 info**（措辞写成「这一侧通常不视为异常」，并在报告第一节
说明原因），判定列写「偏低（通常不视为异常）」，也不会进「需要留意」的清单。

**关键设计**：这个"哪一侧值得留意"的判断**按指标给出，不随区间边界走**。
即使区间是设备印的也一样——InBody 印的「去脂体重 46.7~57.0」会把 58.3 判成
"高于上限"，但肌肉量大的人高于这个以一般人群为基准的上限恰恰是好事。
边界可以来自设备，**"这算不算异常"是关于指标本身的领域判断**。
实现在 `catalog.REF_CONCERN`（一张显式的表），由 `analysis` 覆盖区间自带的默认值。

## 8. `LABEL_CONFLICT` —— 设备的文字判定和它自己的数值打架

**现象**：BMI 24.1 标成"正常"，而报告自印的正常上限是 23.0。或者反过来，
BMI 22.0 标成"超重"。

**为什么是陷阱**：这通常说明设备的判定阈值**用的不是同一套标准**。
亚洲人群的超重界值常用 23，WHO 用 24.9——两台设备、同一份报告的不同栏目
都可能是不同标准。用户看到"正常"两个字就放心了，看到数值才知道已经越界。

**判据**：把设备给的文字判定归到 `low`/`in`/`high` 三档，与按参考区间算出的判定对比。

**怎么读**：规则**不替你决定哪个对**——这取决于你想对照哪套标准。
它只负责把矛盾摆出来，告诉你"这里有两套标准，别只看那个词"。

## 9. `MISSING_DAYS` —— 缺数据的日子按 0 算，日均值就被系统性低估

**现象**：61 天的数据里只有 41 天有步数记录，覆盖率 67%。

**为什么是陷阱**：如果直接算"有数据日的平均步数"，会得到 10000 步，
看起来很好；但真实情况可能是那 20 天手表没戴，实际步数并不低。
反过来，如果把缺失日按 0 算，日均就变成 6700，显得很差。
**两个数都不是真值，但你必须在报告里说清用的是哪个口径。**

**判据**：`agg` 是 `sum`/`mean` 的指标，覆盖率 <70%。

**本项目的口径**：`daily_mean` 用「总和 ÷ 全部跨度的天数」，即**缺失日按 0 算**
（偏保守），同时把覆盖率一并显示出来。缺数据的日子不会被悄悄忽略。

## 10. `DELTA_BELOW_NOISE` —— 别把噪声当成果

**现象**：体重从 74.0 变成 73.8 kg，你很高兴。

**为什么是陷阱**：家用秤的日间波动有几百克，体脂率的单次波动有 1~2 个百分点。
`−0.2 kg` 落在噪声里，**根本没有信息量**。

**判据**：`|变化量| < 该指标的噪声阈值`（阈值定义在 `catalog.py` 的 `noise` 字段）。

**怎么读**：报告会明确写「视为基本未变」。要看真实趋势，用 4 周以上的
滑动平均，别比相邻两次。

## 11. `TREND_TOO_SHORT` —— 两个点不构成趋势

**现象**：一个月内测了两次，画出一条线，说"在下降"。

**判据**：快照类指标少于 2 个点，或时间跨度不足 **14 天**。

**怎么读**：报告会把它列进「不足以判断的部分」。这不是说数据没用，
是说**现在下结论还太早**。

---

## 12. `DEVICE_HANDOVER` —— 换了设备，曲线上的台阶不是身体变化

**现象**：一条几年的曲线在某个时间点突然抬高或压低，然后稳定在新水平。
你可能会读成"状态变好了"或"退步了"。

**为什么是陷阱**：这些工具会**把不同设备、不同时期的数据合并进同一条曲线，
而且不标注换了设备**。不同设备——甚至同一设备换了大版本算法——对同一个生理量的
基线读数并不相同。所以那个台阶很可能是**测量变了**。

**真实数据佐证**：一份 6 年的导出里，最大摄氧量来自 **3 台不同设备**、
静息心率来自 3 台、心率变异性来自 3 台。这些指标近年的"变化"里有多少是设备差异，
**单看曲线是分不出来的**。

**判据**（启发式）：把序列切成"同一来源的连续段"，合并掉过短的碎片，
剩下的段如果来源发生变化，就记一个接替点，并给出日期与新旧设备名。
报告把它合并成**一条**提示（按接替点数量排序，最多列 6 个指标）。

**严重度是 `info` 而不是 `warn`**：它是**读趋势时的口径提醒**，不是数据错误。
warn 要让位给真正需要注意的健康信号。

**怎么读**：只在**同一台设备的时段内**比较趋势。如果确实想知道换设备有没有影响，
可以在换的时候新旧两台同时戴 1–2 周做重叠校验——这是唯一能把设备差异和身体变化
分开的办法。

> 注意这条与第 1 条的分工：第 1 条讲**并发**（同一段时间被两台设备各记一遍，
> 影响数值口径），这一条讲**接替**（不同时期用不同设备，影响跨时间可比性）。
> 两者在报告里是分开处置的。

## 参考区间从哪来（优先级）

这个优先级是本项目的一个核心设计，实现在 `analysis.ref_for_observation()`：

```
1. 被判定的那条观测自带的区间     ← InBody 报告上印的「报告参考范围」
2. 同一 source 最近一条自带的区间  ← 同一台设备这一次没给、上一次给了
3. 内置人群参考表                 ← catalog.py 里带出处的区间，仅在 1、2 缺失时启用
4. 没有                           ← 只报趋势，判定列写「只做趋势」

另外：同一指标出现 >1 个 source 时，跳过 1~4，直接「来源不一致，不做判定」。
```

**为什么设备自带的最优先**：医生看的化验单上每个项目都有自己的参考范围，
体成分设备也一样——它用的是**它自己的模型和它自己的人群**，
通常比通用表更贴近这次测量。而且用户手上的纸质报告印着的就是区间，
报告里用别的区间会让人对不上。

**为什么必须"同源"**：这是第 1 条（`SRC_MIXED`）的直接推论。家用秤的 21.2% 体脂
配上 InBody 的 10~20% 区间，会输出一个看起来专业、实际无意义的"高于参考上限"。
设备自带区间之所以优先，前提是它最贴近**那台机器**的模型——跨设备就失去了这个前提。

第 4 档不是失败，是诚实。**没有区间就只做趋势**，比硬编一个"正常"出来强。

内置区间的出处都会原样出现在报告里（`RefRange.source`），
`health-report metrics` 可以一次看全。它们全部**只是筛查参考，不构成诊断**。

## 本项目明确**没有**做的判断

写下来是为了让你知道边界在哪：

| 没做的事 | 为什么 |
|---|---|
| 诊断任何疾病 | 生物电阻抗估算不是诊断依据；本项目不是医疗设备 |
| 推荐药物、补剂或剂量 | 超出范围 |
| 判断"这次测量是水肿导致的" | 只能指出水分超上限这个**事实**，病因判断需要临床信息 |
| 声称设备的参考模型变了 | 只能给"隐含基准漂移"这个可量化证据；不够 5% 就只说口径（见第 5 条） |
| 反查设备用的计算公式 | 有趣（例如用去脂体重反推 Katch-McArdle 公式能验证基础代谢率），但是 v0.2 的事 |
| 给出热量缺口或蛋白质摄入的具体数值建议 | 那需要完整的饮食与训练信息，不是体成分数据能支撑的 |
