## 它解决什么问题

你已经有 Apple Watch 记下的步数、心率、睡眠、VO₂max，可能还有一份体测报告和一台家用秤。
每个 App 都能给你画个图。

**但它们都不会告诉你：哪些数字不能横着比。**

下面每一条都是在一份 6 年、2600 多天的真实导出上真实出现过的情形：

- **曲线上的那个台阶，可能是换了设备。** 同一指标在多年里可能来自好几台设备，
  Apple 会把它合并进同一条曲线，**而且不标注换了设备**。那份导出里，最大摄氧量来自
  **3 台**不同设备、静息心率来自 3 台、心率变异性来自 3 台。这些"变化"里有多少是设备差异，
  单看曲线分不出来。
- **步数被两台设备各记了一遍。** iPhone 和 Apple Watch 各自记录步数，时间区间高度重叠。
  无条件累加会让总量放大约 **1.44 倍**（那份导出里 57.4% 的天数有多来源记录）。
  更坏的是**它不是均匀偏差**——只有单来源的那些天是对的，于是"那天戴了哪台设备"
  污染了逐日对比。
- **静息心率偏低，天天报警就等于没有报警。** 长期做耐力训练的人静息心率本来就在 50 出头。
  如果按"低于筛查下限就报异常"，那份导出里**大多数日子**都要报警，
  真正该看的那一条会被淹没。
- **睡 6 小时和"1 点睡、7 点起"不是同一件事。** 时长可以靠某一天补回来，
  睡眠中点的漂移补不回来。只看总时长会漏掉后者，而后者与恢复状态的关系更稳。
- **睡眠算在哪一天，会决定你能不能看出关联。** Apple 把一夜睡眠记在**醒来那天**。
  归错日期，"睡得好→第二天心率低"这种关系会被打乱成噪声。
- **Apple 导出里几乎没有参考区间。** 所以多数指标的正确默认值是"只做趋势"。
  **硬编一个"正常"出来，比留白伤害大得多。**

`health-report` 把这些"算对了但读错了"的情形做成**可执行的检查**：
**13 条带机器码的规则**，每条都会在报告里带具体数字告诉你怎么读。
规则的完整说明在 **[docs/PITFALLS.md](docs/PITFALLS.md)**——那个文件比代码重要。

## 跟别的健康数据分析工具比，四点不同

### 1. 参考区间不是必需品，但**必须和读数同源**

```
被判定的那条读数自带的区间  >  同一设备最近提供的区间  >  内置人群参考表  >  没有
```

Apple 导出基本不带区间，所以大多数指标会落到内置人群表，或者干脆落到最后一档。
最后一档不是失败，是诚实：`HRV(SDNN)` 和深睡时长**没有公认的通用正常范围**
（个体差异太大），这些指标的报告判定列写「只做趋势」，报告里还有专门一节列出它们。

如果你额外喂给它一份体成分报告（InBody 等），**报告上印的区间会被解析并优先使用**——
它用的是自己的模型和自己的人群。但这里有个前提：

> **区间只能用于它自己那台设备的读数。** 用家用秤的 21.2% 体脂去套 InBody 的 10~20% 区间，
> 会得出一个看起来专业、实际无意义的"高于参考上限"。所以当最新读数来自另一台设备、
> 而它自己没给区间时，报告会写「来源不一致，不做判定」，而不是硬套一个上去。

### 2. 区分「正常参考」「活动目标」「筛查阈值」

这是这类工具最常见的错误：把公共卫生建议渲染成医学判定。

| 性质 | 例子 | 超出时怎么说 |
|---|---|---|
| `range` 正常参考区间 | 睡眠时长 7~9 小时 | `高于参考上限` |
| `screen` 筛查阈值 | 腰围男性 ≥90 cm | `超出筛查参考范围`（并说明不等于诊断） |
| `goal` 活动量目标 | 步数 ≥8000 | **`未达目标`**（绝不说"异常"） |

你今天只走了 6500 步，那不是"指标异常"，只是没到常见的建议量。

### 3. 同一区间，两侧的意义不一样

还有一层更隐蔽，而且它决定报告会不会变成"狼来了"：

**有一批指标只有一侧是真正需要留意的信号**，落在另一侧是常见、甚至好事。
静息心率偏低是长期耐力训练者的常态；去脂体重、骨骼肌量、蛋白质偏高是肌肉量充足；
血氧偏高不是问题。把不需要留意的那一侧也报成"异常"，代价不只是多一条无用提示——
**它会把真正该看的那条淹没。**

所以这类越界会**降调**：措辞写成「偏低（通常不视为异常）」，第一节说明原因，
也不进需要留意的清单。

关键设计：这个判断**按指标给出，不随区间边界走**。即使区间是设备印的也一样——
体成分仪印的「去脂体重 46.7~57.0」会把 58.3 判成"高于上限"，而肌肉量大的人
高于这个以一般人群为基准的上限，恰恰是好事。**边界可以来自设备，
"这算不算异常"是关于指标本身的判断**（实现在 `catalog.REF_CONCERN`）。

### 4. 规则层先算，模型后说

**所有数值结论都由确定性代码得出。语言模型只负责解释，不允许它算数。**

它拿到的是 `build_facts()` 输出的**结构化摘要**——里面每一个数字都是代码已经算好的，
连"训练总时长""各指标覆盖率"这种汇总也提前算好给它，免得它自己动手。
用 `--json facts.json` 可以把这份摘要原样存下来，**在发出去之前自己过一遍**。

这意味着：**没有 API key、完全离线，报告依然完整**，因为所有结论都在「规则层结论」
那一节里由代码写好了。AI 顶多是在旁边多写一段白话。没有 key、网络不通、模型返回垃圾，
都不影响报告的可信部分。

开启后它写两件事：把上面的数字讲成人话，以及**下一步能做什么**。但那类建议被
**严格限制在「改善数据可比性」的范围内**（固定用同一台设备、统一测量条件、增加数据点、
拉长观察窗口、复测确认），因为那才是这份事实能支撑的建议。它不会给医疗、营养或训练
处方——不写热量缺口、蛋白质克数、补剂或剂量；遇到这类情形它只能说「这一点需要专业评估」。

## 安装

核心**零第三方依赖**，标准库就能跑。

```bash
# 推荐：从 git 装到隔离环境
pipx install "git+https://github.com/alpsgangster/Health-report"

# 或者克隆下来直接用，不装任何东西
git clone https://github.com/alpsgangster/Health-report
cd health-report
PYTHONPATH=src python -m health_report demo
```

**Windows 用户**：不用记 `PYTHONPATH`，仓库根目录有个启动器，双击或在 cmd 里直接跑：

```cmd
health-report.cmd demo
health-report.cmd report "..\apple_health_export\导出.xml" -o 我的报告.md
```

它只做两件事：把 `src/` 加进 `PYTHONPATH`、把输出编码设成 UTF-8（不加这个，
中文控制台遇到报告里的 🟠🔵 会报编码错）。**不需要 pip install。**

可选加速：Apple 的 `export.xml` 有几 GB 时，`lxml` 会快好几倍。
**不装也能跑**（自动退回标准库）：

```bash
pipx install "health-report[fast] @ git+https://github.com/alpsgangster/Health-report"
```

## 用法

### 先看它能做什么

```bash
health-report demo                          # 用内置合成数据出一份完整报告
health-report demo --findings               # 顺便打印命中了哪些规则
health-report metrics                        # 列出支持的 77 个指标与内置参考区间
health-report inputs                         # 说明支持哪些输入格式
```

### 用自己的数据

只有 Apple 导出也能出一份完整报告——这是**唯一必需**的数据源。

```bash
# Apple 健康导出（iPhone → 健康 App → 头像 → 导出所有健康数据）
health-report report 导出.zip -o 我的报告.md

# 可选：再补一份体测报告（从报告上抄成长格式 CSV，格式见 docs/DATA_FORMATS.md）
health-report report 导出.zip inbody.csv -o 我的报告.md

# 只做解析，产出结构化 CSV/JSON 自己再分析
health-report parse 导出.zip -o health_out/

# 显式开启 AI 解读（可选）
health-report report 导出.zip --llm

# 打包一份「准备发给模型的内容」自己先检查
health-report report 导出.zip --json facts.json --no-llm

# 客户交付形态：自包含 HTML（内联 SVG 图表），浏览器里打印即 PDF
health-report report 导出.zip --html 我的报告.html
```

### HTML 报告：打印就是 PDF

`--html` 出一份**自包含**的单文件 HTML：内联 CSS、**手写 SVG 图表**、
**零外部资源、零 JavaScript**。用浏览器打开 → `Ctrl+P` → 另存为 PDF 就是最终交付物。

- **9 个小节**：封面 / 数据可信度提示 / 指标总览 / 睡眠 / 恢复与负荷 /
  指标之间的关联 / 活动与训练 / 规则层结论 / AI 解读（可选）+ 方法与口径附录
- **图表全部手写 SVG**，不引入任何绘图依赖（"零依赖"是这个项目的卖点，
  不能为了画图把它破坏掉）：
  - 月度中位数趋势线 + **四分位带**，参考区间按性质换线型（`range` 实线框 /
    `screen` 虚线框 / `goal` 只在目标值画点线）
  - **设备接替标记**：把 `handovers` 的切换日期画成竖直虚线并标注新旧设备名
  - 睡眠分期构成、睡眠规律性散点（刻度还原成钟点）、关联对比柱状图、
    步数 vs 目标、数据覆盖率、体检式判定总览条
- **降采样与聚合**：6 年数据按月聚合（1910 天 → 79 个月度点），
  散点图超过 1200 点等间隔抽样并在图注说明——不会画 2600 个点
- **黑白也能读**：所有信息都有文字或线型，不只靠颜色；"差异在噪声内"用斜纹，
  「未达目标」与「越界」是两档不同视觉
- 生成很快：真实 6 年导出 **0.07 秒**（解析占 33 秒的大头）

> ⚠️ 打印时**勾选「背景图形」**，否则浅底色与斜纹会被浏览器丢掉（这是浏览器
> 打印选项，CSS 强制不了）。页码请用浏览器的**页眉和页脚**选项——`@page` 的
> 页码盒只有 Prince/WeasyPrint 这类分页引擎支持，Chrome/Edge 会忽略它。
> 我们不假装有页码。

### Apple 的多设备记录不会被静默双计

这是 Apple 导出里最容易踩的坑：**iPhone 和 Apple Watch 各自记录步数，时间区间高度重叠**。
Apple 健康 App 显示的是去重后的值，但导出文件里两套记录都在。

在一份 1910 天的真实导出上实测：

| | |
|---|---|
| 有多来源记录的天数 | **1096 天（57.4%）** |
| 无条件累加 vs 按主设备取值 | **放大 1.44 倍** |

最干净的一次证据是同一天被两台设备各记了约 4.5 万步，累加后报出 **9 万步**。

> 绝对总量这里刻意略去（那是个人信息）；关键是**倍数**，以及它**不是均匀偏差**——
> 只有单来源的天数是对的，于是"那天戴了哪台设备"污染了逐日对比。

HealthKit 的重叠区间去重算法**没有公开规范**，所以本项目不去猜一个算法，而是把口径
变成显式选择，并把差异摆出来：

```bash
health-report report 导出.xml                      # 默认：主设备优先
health-report report 导出.xml --prefer-source "Apple Watch"   # 指定主设备
health-report report 导出.xml --source-policy per-day-max     # 或每天取各来源最大值
health-report report 导出.xml --source-policy sum            # 无条件累加（会算高，仅对照）
```

报告里会为每个受影响的指标写一条说明，给出各口径下的总量和倍数。详见
[docs/PITFALLS.md](docs/PITFALLS.md) 第 1.5 节。

> 注意：快照类指标（体重、体脂率）的多来源是**两台设备对同一个东西给了不同的数**——
> 那是分歧，不是口径问题。这类指标**照常判定**，但区间只在同源可得时使用；
> 拿不到就写「来源不一致，不做判定」，并且这条线索会在报告里明确给出。

### 曲线上的台阶可能是换了设备（设备接替检测）

Apple 会把不同设备、不同时期的数据合并进同一条曲线，**并且不标注换了设备**。
不同设备——甚至同一设备换了大版本算法——对同一个生理量的基线读数并不相同。

所以报告里有一条 `DEVICE_HANDOVER` 规则：把序列切成"同一来源的连续段"、合并掉过短的碎片，
剩下的段如果来源发生变化，就记一个接替点并给出日期与新旧设备名（合并成**一条**提示，
按接替点数量排序）。在「规则层结论」那一节还会有一个**跨设备可比性**小节，
把受影响的指标逐条列出来。

它取 `info` 而不是 `warn`：这是**读趋势时的口径提醒**，不是数据错误——
warn 要让位给真正需要注意的健康信号。

### 睡眠规律性，以及睡眠与次日恢复的关联

报告会算**睡眠中点（入睡与醒来的中点）的标准差**，这是作息规律性的单一最佳概括——
它同时包含"几点睡"和"几点起"。分档阈值（30 / 60 分钟）在报告里被明确标注为**经验分档、
不是诊断标准**，并且只说明离散程度、不判断好坏。

还有一组**确定性计算出来的关联**（相关，不是因果）：

- 睡眠时长 → **次日**静息心率 / 心率变异性
- 白天步数 → 当晚睡眠时长
- **训练日 vs 非训练日**：静息心率、HRV、睡眠时长

每条都给两组的中位数对比（比相关系数好懂）和相关系数。证据等级看的是
**效应大小相对于该指标的测量噪声**，不是相关系数——所以会出现"相关系数很高、
等级却不高"的情况，那表示关系一致但幅度还不到设备的重复测量误差量级，
报告里会解释这一点。

> 为什么这件事值得单列：**规律性比时长更容易改，而且与恢复状态的关系更稳。**

### 设备名里的姓名会被隐去

Apple 的默认设备名带机主姓名（「某某的 Apple Watch」）。本工具会把来源名打印进报告，
而报告天然是要分享的——所以默认隐去姓名部分，保留器械名（你需要靠它分辨设备）：

```
<机主>的Apple Watch     ->  Apple Watch
（不含姓名前缀的自定义设备名）  ->  原样保留
```

要完全不脱敏（仅本地调试）：`--show-source-names`。

### AI 解读：四种后端，**会自动挑，但绝不自动外发**

AI 那一节是**可选**的（不开启报告也完整）。开启时后端自动探测，按这个顺序：

| 顺序 | 后端 | 数据去哪 | 自动采用？ | 你要做什么 |
|---|---|---|---|---|
| 1 | 环境变量配置的**云端端点** | 你配的那个地址 | ✅（配了就是知情） | 填一个 API key |
| 2 | **本机模型**（Ollama / LM Studio / llama.cpp） | **不出本机** | ✅ | 启动它即可（默认探测 `127.0.0.1` 的 11434 / 1234 / 8080） |
| 3 | **本机已装的 AI 工具**（DSH / Claude Code / Codex） | 对应厂商（DeepSeek / Anthropic / OpenAI） | ❌ **要显式开口** | `--llm` 或 `--ai-backend dsh` |
| 4 | 都没有 | —— | —— | 纯规则报告，文字偏机械但内容完整 |

```bash
health-report report 导出.xml                     # 只会在「不出本机」或你已配置的后端里挑
health-report report 导出.xml --llm               # 显式要 AI：这才解锁第 3 类（会外发）
health-report report 导出.xml --ai-backend dsh    # 或直接点名
health-report report 导出.xml --ai-backend none   # 只要纯规则报告，完全不联网
health-report report 导出.xml --no-llm            # 同上
```

云端端点也可以是任何 OpenAI 兼容服务：

```bash
export HEALTH_REPORT_API_KEY="你的key"
export HEALTH_REPORT_BASE_URL="https://api.deepseek.com"    # 可选
export HEALTH_REPORT_MODEL="deepseek-chat"                    # 可选
```

> ⚠️ **"本机装好的 AI 工具"不等于"模型在本地"。** DSH / Claude Code / Codex 是本地客户端，
> 模型在云端——用它们等于把算好的摘要发给对应厂商。所以**默认不会用它们**，
> 需要你显式开启，而且每次运行都会在终端打印 **「数据将发送至：<厂商>」**。
> 要真正不出本机，用第 2 种（本机模型）。
>
> 这条限制的由来：早期版本让自动探测一路走到底，结果在装了 DSH 的机器上，
> `health-report report 导出.xml`（既没配 key、也没加 `--llm`）会**静默把摘要发出去**。
> 默认静默外发对"隐私优先"来说是不能接受的，所以改成了显式开口。
> 回归测试在 `tests/test_llm_backends.py::TestAutoNeverLeaksData`。

### 编造的数字进不了报告（硬校验）

接任何模型都有一个风险：它自己编一个数值。所以 AI 写的每一个数字都会**逐个回查**
`facts`（那份算好的摘要）——找不到来源，含那个数字的**整句会被删掉**，并在报告里说明
删了几处、为什么删。若删完剩下的太单薄，就整段丢弃、改用规则层原文。

宁可报告里没有 AI 那一段，也不能出现一个编造的数值。

**同时也要避免误杀**——把一整段正确的解读丢掉，比漏抓更糟。所以这些**合法写法**会被认：
千分位（`1,910` 或 `11 534`）、`1.08 万` 这类量级写法、把事实值按位舍入（`6.28937…` 写成
`6.29`）、以及 Markdown 小节号（`### 2.2`）。但**编造的测量值照样会被抓住**
（摘要里是 `61.0`，你写 `58.2` → 删）。

> 取舍说明：小整数（1~12，用于"两台设备""第 2 点"这类计数与序号）在白名单里放行，
> 所以编造**计数**可能漏过；这道校验针对的是**编造的测量值**。

## 支持的输入

| 输入 | 形式 | 说明 |
|---|---|---|
| **Apple 健康导出**（唯一必需） | `导出.zip` / `export.xml` / `apple_health_export/` | 流式解析，几 GB 也不吃爆内存。含每日指标、睡眠分期、每次训练 |
| **InBody 等体成分报告**（可选） | 长格式 CSV | 日期列数量不限；**报告自带的参考范围会被解析并优先使用**；模糊匹配指标名 |
| **通用长格式 CSV**（可选） | `date,metric,value,unit,source` | 任何设备的万能入口，手抄数据也能进 |

单位在解析阶段就归一（磅→kg、英里→km、千焦→kcal…），下游永远见不到"有的用磅有的用公斤"。
细节和样例见 **[docs/DATA_FORMATS.md](docs/DATA_FORMATS.md)**。

## 隐私

健康数据是最敏感的个人数据之一。Apple 的导出包里除了体重心率，
还有 `workout-routes/*.gpx`——**你每次跑步的 GPS 轨迹，能定位到你家门口**。

- **默认完全离线。** 没有遥测、没有版本检查、没有崩溃上报、没有"匿名统计"。
  想 100% 保证：加 `--no-llm`。
- **联网只发生在你显式开启 AI 解读时**，且只发**算好的摘要**，不发原始记录。
  用 `--json` 先自己看一遍再决定。
- 密钥只从环境变量读，**不落盘、不打印**，日志里会遮蔽成 `sk-a***`。
- 报告里的人名会被隐去（见上文「设备名里的姓名会被隐去」）。
- 仓库的 `.gitignore` 默认拒绝一切真实数据文件，CI 里有个 `隐私守卫` job
  每次 push 都检查有没有误提交。

完整说明（含威胁模型：这个项目**不**防什么）见 **[docs/PRIVACY.md](docs/PRIVACY.md)**。

## ⚠️ 这不是医学诊断

本工具对**自我追踪的测量值**做描述性汇总。它不是医疗器械，
不诊断、不治疗、不预防任何疾病，输出不能替代合格医疗专业人员的评估。

内置的参考区间是**带出处的人群筛查参考**，只用于定位，不是诊断阈值；
当测量设备或化验单自带参考范围时，以设备/化验单的为准。
报告里所有区间都会注明出处，方便你核对。

如果你出现不明原因的体重/肌肉下降、持续疲劳、食欲或内分泌相关症状，**请就医**，
不要用这个工具的解释替代。
